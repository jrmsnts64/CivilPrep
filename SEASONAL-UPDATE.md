# CivilPrep v2.6 — Seasonal updates (GitHub Pages)

## Install on the existing public `jrmsnts64/CivilPrep` repository
1. Complete any unfinished session before installing or approving a new bank. Keep a backup of your current repo. The package does not include user localStorage records.
2. Extract the full ZIP, then upload its **contents** (not the ZIP or the enclosing folder) to the existing repository root. Existing index.html, sw.js and questions.js must be in the same root. Do not delete other needed files. Make sure `.github/workflows/civilprep-seasonal.yml` and `.nojekyll` are present; hidden files sometimes need separate upload. If the workflow is missing, use GitHub Add file > Create new file, enter `.github/workflows/civilprep-seasonal.yml`, paste the packaged YAML, and commit to main.
3. In repository Settings > Pages, change Build and deployment > Source to **GitHub Actions**. The workflow deploys a static artifact directly, since a bot commit using GITHUB_TOKEN does not itself trigger a branch-based Pages build. In Actions, enable workflows if asked. The workflow uses the built-in token, not a personal API key. Repository policy must permit its requested contents/issues writes and Pages deployment. If protected main rejects the bot commit, review the policy or use an owner-approved PR workflow instead; do not disable protections just to make the job succeed.
4. In Actions > CivilPrep seasonal updates and Pages > Run workflow, select main and leave `approve_cycle` empty and `acknowledge_sources` unchecked. Inspect the run log and status.json. Open the existing Pages URL after successful deployment. No APK is built by this workflow.
5. On the phone, finish any session before choosing Update available or reopening the app. Open Announcements > Question bank updates. Status displays the installed and published bank separately. If online monitoring fails, the last successful source check is retained. The offline bank remains available.

## Automated cycle
- Every Monday at 09:23 Philippine time (01:23 UTC), and on main pushes or manual dispatch, GitHub Actions checks seven public reference pages. It detects changes by hashing normalized text or the CSC CSE advisory link list. First successful fetch establishes a baseline. Blocked/failed sources are reported as unavailable. No Facebook scraping or copying. Public independent guides are topic references, not official exam content.
- On the first run following a known CSE date (Asia/Manila), stage 20 original replacement items (5 each in Clerical, Numerical, Analytical, Verbal), plus a review reminder issue. A single pending draft is held until approved; later dates queue. The 2027 calendar contains March 14 and August 8. New official advisories are flagged and linked. To add a future confirmed cycle, edit exam-config.js calendar entries and verify the nationwide schedule. Monitor does not assume a new date or an amended scope from a page hash. Regional guidance and testing center links still require a cycle-specific editorial update.
- Drafts are reproducible rule-based templates, not reconstructed exam questions or newly scraped content. General Information needs direct primary-source review, especially after new laws or coverage changes. The checker does not determine semantic accuracy of every existing item, and difficulty labels are practice estimates. A hash change may be cosmetic. A hash match does not prove the bank is current.

## Owner approval and deployment
1. Review `updates/candidates.json` in the repository, check each question, answer, explanation and difficulty. Inspect `updates/status.json` for reference changes and review General Information, CSC scope, and region guidance. Update factual content manually from reliable sources if needed. Do not label material official CSC questions. CSC does not publish or endorse reviewers and discourages circulating actual test content.
2. If the staged pack is satisfactory, open Actions > CivilPrep seasonal updates and Pages > Run workflow. Enter its **completed exam date** in `approve_cycle` exactly as shown in `updates/candidates.json`. The workflow rejects stale or altered deterministic drafts. Only approve after editorial review. If factual/manual edits are required first, a draft may need regeneration; do not approve a mismatched draft. Back up the draft and remove `updates/candidates.json` through a reviewed commit to regenerate it (only for an unpublished cycle).
3. Use `acknowledge_sources` only after reviewing flagged sources and making any necessary editorial changes. If a source is unavailable, its unresolved flag is retained. Close review issues when resolved.
4. On approval the workflow replaces 20 slots, preserves difficulty counts and 90 variants, increments the bank/cache version and deploys the revised bank. Old completed scores remain in local storage. New IDs prevent a retired item's history from being assigned to a different item. Old retired bookmarks may no longer appear, and unfinished sessions containing retired items cannot resume. Finish sessions before update. No user credentials or scores are uploaded.

## Limits and checks
- Initial bank is v2.5: 500 base slots, 90 Professional variants, 25 previously revised slots. This package adds infrastructure, not new live questions. The full bank still needs independent content verification before monetization.
- Test results: simulated March and August cycle detection, draft generation, publish, no duplicate publication, 590 records and preserved category/tier totals; JavaScript syntax checked. Live external fetch, GitHub Actions deployment, offline upgrade on actual phones, and complete question correctness not tested here.
- Standard hosted Actions runners for public repositories are generally free. GitHub Pages is for noncommercial testing, not the future monetized product. Scheduled public workflows may be disabled after 60 days of inactivity or delayed. Check Actions periodically and re-enable as needed. A failure or a changed page layout must not be represented as a verified question update.
